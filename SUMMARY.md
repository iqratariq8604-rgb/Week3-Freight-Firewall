# Summary — Approach and Reasoning

For Week 3 I built a network segmentation plan and firewall policy for ABC Freight Forwarders, a fictional independent freight forwarder. The main risk I focused on was that every device in a small logistics office usually sits on one flat network, so a driver's phone on guest Wi-Fi could reach the same billing system the finance team uses. Freight companies are frequent targets of invoice fraud and ransomware, so protecting the billing system was the priority.

My approach was to decide who actually needs the billing system and give access only to them. I divided the network into five zones by IP range: IT, Office, Finance, Warehouse and Guest. Only Finance (for invoicing) and IT (for maintenance) got an allow rule on port 8080. Guest and Warehouse got explicit block rules, and Office was left to Windows' default deny. I used the laptop as the company server and one Kali Linux VM that held a separate IP for each zone, so I could test all five zones from one machine.

Windows Event Viewer was the tool I used to prove the policy works. Logging for firewall connections is off by default, so I enabled it with auditpol first. After the rules were in place, all five zone tests passed. Event 5156 showed Finance being allowed to port 8080, Event 5152 showed Guest being dropped, and the portal's own log confirmed that only Finance and IT ever reached the service. One challenge was log noise: the Security log had more than 27,000 events, mostly my laptop's own internet traffic, so I wrote XPath filters by Event ID, IP address and port to find the exact evidence.

The most important test was tampering. Acting as an insider with admin rights, I disabled the Guest block rule and added an allow rule named "Windows Update Helper" so it would look harmless. Guest could then open the billing portal, which showed that segmentation can be broken with just two commands. However, Event Viewer recorded both changes (Events 4947 and 4946) 35 seconds apart, and the Rule IDs matched the original rules. I reversed the changes, the fix was also logged (4948 and 4947), and Guest was blocked again on retest.

The key lesson is that a firewall policy is only as strong as the monitoring around it. The logs showed what changed and when, but not who did it, so my next improvement would be PowerShell Script Block Logging and automatic alerts on firewall rule changes through a SIEM.
